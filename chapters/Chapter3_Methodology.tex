\subsection{Функциональ шаардлага}

Системийн функциональ шаардлагад дараах боломжуудыг багтаав:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item Зөвхөн өөрийн сургуулийн оюутан, оюутны кодоо ашиглан нэвтрэх;
    \item Гадны этгээд хэрэглэгчээр бүртгүүлэхгүй, контентуудыг зөвхөн харах эрхтэй байх;
    \item Зарим модуль нийтэд ил бус, эсвэл хязгаарлагдмал байдлаар байх;
    \item Report (bug, user), feature request гэсэн тусдаа сувгаар хэрэглэгч санал хүсэлтээ илгээх боломжтой байх;
    \item Флашкарт үүсгэх, засах, хуваалцах;
    \item Толь бичиг ашиглах болон шинэ үг нэмэх;
    \item Блог, нийтлэл, төсөл нийтлэх;

\subsection{Функциональ бус шаардлага}

Системийн функциональ бус шаардлагад өгөгдлийн аюулгүй байдал, веб ба мобайл синхрончлол, өргөтгөх боломжтой архитектур, гүйцэтгэлийн хурд, найдвартай байдал зэрэг багтана. Эдгээрийг техникийн түвшний тодорхой зорилтуудаар дараах байдлаар тодруулсан:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item нэг хэрэглэгчийн энгийн асуулгын (query) хариу өгөх хугацааг практик хэрэглээнд мэдрэгдэхүйц сааталгүй байлгах;
    \item веб болон мобайл дээр өгөгдлийн тасралтгүй байдлыг API-ийн нэг эх сурвалжаар хангах;
    \item контентын шинэ модуль нэмэгдэхэд өгөгдлийн загварыг дахин үндсээр нь эвдэхгүйгээр өргөтгөх боломжтой байх.
\end{itemize}

\section{Системийн загварчлал}
% ─────────────────────────────────────────────

Шаардлагын дагуу системийн логик бүтэц, хэрэглээний урсгал, өгөгдлийн бүтэц, архитектурын шийдэл болон хэрэглэгчийн интерфейсийн загварыг нэгдсэн байдлаар боловсруулсан. 

\subsection{Use Case диаграм}

Use case загварчлалын хүрээнд оюутан, багш, админ гэсэн гурван үндсэн хэрэглэгчийн үүрэг болон тэдгээрийн гол үйлдлүүдийг тодорхойлсон:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item \textbf{Оюутан:} бүртгүүлэх, нэвтрэх, карт үүсгэх, давтах, нийтлэл/асуулт нийтлэх, төслийн тэмдэглэл хөтлөх, сургалт/тэмцээнд оролцох;
    \item \textbf{Багш:} сургалт үүсгэх, агуулга бэлтгэх, чанарын хяналт хийх, зөвлөмж өгөх;
    \item \textbf{Админ:} хэрэглэгчийн эрх удирдах, агуулгын бодлого хэрэгжүүлэх, тайлан хянах.
\end{itemize}

Системийн төвд \textit{Хэрэглэгч} байрлаж, мобайл талд нэр томьёо суралцах урсгал (флашкарт, толь бичиг), веб талд бүтээмжийн урсгал (нийтлэл, төсөл, сургалт, тэмцээн, ранкинг) байрласан. Админ болон багш нь чанарын хяналт, агуулгын баталгаажуулалт, зохион байгуулалтын үүргийг гүйцэтгэхээр загварчлагдсан.

\subsection{Өгөгдлийн загварын зарчим}

Өгөгдлийн загварыг төлөвлөхдөө дараах \textbf{дөрвөн зарчмыг} баримталсан:

\begin{keybox}[Өгөгдлийн загварын 4 зарчим]
\textbf{Entity тусгаарлалт} $\cdot$ \textbf{Холбоосын ил тод байдал} $\cdot$ \textbf{Өсөлтөд бэлэн байдал} $\cdot$ \textbf{Аудит мөр} — эдгээр нь урт хугацаанд засварлаж, өргөтгөж болох тогтвортой өгөгдлийн бүтэц бий болгох цөм зарчмууд юм.
\end{keybox}

\begin{enumerate}[leftmargin=2em, itemsep=0.25em]
    \item \textbf{Entity тусгаарлалт:} хэрэглэгч, контент, давталтын логик, оролцооны үнэлгээ тусдаа хүснэгтүүдэд байрлах;
    \item \textbf{Холбоосын ил тод байдал:} нийтлэл-толь бичиг, карт-толь бичиг, хэрэглэгч-контент хоорондын холбоог гадаад түлхүүрээр тогтвортой хадгалах;
    \item \textbf{Өсөлтөд бэлэн байдал:} шинэ модуль нэмэхэд үндсэн хүснэгтийн бүтцийг эвдэхгүйгээр өргөтгөх боломжтой байх;
    \item \textbf{Аудит мөр:} контент үүсгэсэн, зассан, баталгаажуулсан хугацааны мэдээллийг хадгалах.
\end{enumerate}

\subsection{Архитектурын шийдэл}

Системийг клиент–сервер архитектур дээр суурилан боловсруулсан. Веб болон мобайл аппликейшн нь RESTful API-гаар дамжин backend сервертэй холбогдож, өгөгдлийг Supabase (PostgreSQL) өгөгдлийн санд хадгалдаг. Архитектурын үндсэн бүрэлдэхүүнүүд нь:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item Front-end (Web + Mobile App);
    \item Backend API;
    \item PostgreSQL өгөгдлийн сан;
    \item Cloud storage (зураг, аудио, файл хадгалах).
\end{itemize}

Spaced Repetition алгоритмыг клиентийн бус backend түвшинд хэрэгжүүлж, хэрэглэгч бүрийн давталтын түүх дээр үндэслэн дараагийн харагдах картыг динамикаар тодорхойлдог байдлаар зохион байгуулсан.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.98\textwidth]{pictures/system-architecture.png}
\caption{FutureHub системийн хялбарчилсан клиент-сервер архитектур}
\label{fig:system-architecture}
\end{figure}

Зураг~\ref{fig:system-architecture}-т архитектурын мэдээллийн урсгалыг харуулав. Клиентээс API хүсэлт ирж, backend нь өгөгдлийн (metadata) асуулгыг PostgreSQL-с, файл төрлийн агуулгыг cloud storage-оос тус тус шийдэж хэрэглэгчид буцаадаг. Ийм хуваарилалт нь мультимедиа контент ихсэх үед өгөгдлийн сангийн ачааллыг тусгаарлах давуу талтай.

Архитектурын сонголтын давуу талыг тоймлон авч үзвэл:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item веб ба мобайл дээр бизнес логикийг backend түвшинд төвлөрүүлснээр давхардал буурна;
    \item өгөгдөл болон файлын урсгалыг тусгаарласнаар өргөтгөхөд хялбар;
    \item модуль нэмэхэд API endpoint нэмэх замаар шат ахиулан хөгжүүлэх боломжтой;
    \item хэрэглэгчийн ахиц, contribution зэрэг тооцоог нэгдсэн байдлаар хийх боломжтой.
\end{itemize}

\begin{insightbox}[Архитектурын гол давуу тал]
\textbf{Backend-төвтэй} бизнес логик + \textbf{тусгаарлагдсан} файлын агуулах + \textbf{API-төвтэй} өгөгдлийн урсгал = \textit{Нэг эх сурвалж, олон клиент} гэсэн зарчимд тулгуурласан \textbf{өргөтгөх боломжтой}, \textbf{засварлахад хялбар} архитектур.
\end{insightbox}

\subsubsection{Аюулгүй байдлын аргачлал}

Платформын аюулгүй байдлыг хангахад дараах таван механизмыг ашигласан:

\begin{enumerate}[leftmargin=2em, itemsep=0.25em]
    \item \textbf{Нэвтрэлтийн хяналт:} Supabase Auth-ийн JWT токен дээр суурилсан session удирдлага; оюутны бүртгэлд зөвхөн сургуулийн имэйл хаягийг зөвшөөрсөн;
    \item \textbf{Role-based access control (RBAC):} оюутан, багш, админ гэсэн үүрэг бүрт тусдаа зөвшөөрлийн бодлого тогтоож, RLS бодлогоор өгөгдлийн сангийн хүснэгт тус бүрт мөрийн түвшний хяналтыг суулгасан;
    \item \textbf{Оролтын баталгаажуулалт:} API endpoint бүрт шаардлагатай талбар, өгөгдлийн төрөл, уртын шалгалтыг хийж, буруу оролтыг эрт шатанд татгалзах;
    \item \textbf{HTTPS нэвтрэлт:} бүх клиент-сервер харилцааг шифрлэгдсэн сувгаар гүйцэтгэх;
    \item \textbf{Мэдрэмтгий өгөгдлийн хамгаалалт:} нууц үг, токен зэрэг мэдрэмтгий мэдээллийг environment variable-д хадгалж, эх кодод шууд оруулахгүй байх.
\end{enumerate}

\subsubsection{API загварын ерөнхий зарчим}

API дизайнд дараах дөрвөн зарчмыг баримталсан:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item resource-oriented endpoint (жишээ нь \texttt{/cards}, \texttt{/articles}, \texttt{/dictionary}, \texttt{/contests});
    \item CRUD урсгалын стандарчилсан хэрэгжилт (create/read/update/delete);
    \item authentication болон authorization-ыг хэрэглэгчийн role-той уялдуулах;
    \item frontend талд дахин ашиглахад хялбар, тогтвортой response бүтэц.
\end{itemize}

Supabase-ийн Row Level Security (RLS) бодлогыг ашиглан хүсэлт бүрийг хэрэглэгчийн role-д тохирсон зөвшөөрлийн хүрээнд гүйцэтгэхийг баталгаажуулсан. Ингэснээр application түвшний authorization логикийг өгөгдлийн сангийн түвшинд хийж, нэмэлт middleware давхаргын хэрэгцээг бууруулсан.

\subsection{UI/UX загвар дизайн}


Хэрэглэгчдэд ээлтэй, ойлгомжтой интерфейс боловсруулах зорилгоор wireframe болон prototype загваруудыг Figma дээр боловсруулсан. Давталтыг илүү сонирхолтой болгох зорилгоор Quizlet, Duolingo маягийн \textit{gamified review} механикийг UI дээр тусгасан.

UI/UX боловсруулахад дараах \textbf{дөрвөн зарчмыг} удирдлага болгосон:

\begin{defbox}[UI/UX-ийн 4 зарчим]
\textbf{Task-first} — хамгийн бага алхмаар нэг даалгавар.
\textbf{Consistency} — веб ба мобайлд ижил нэршил, логик.
\textbf{Feedback visibility} — үйлдлийн үр дүн шууд харагдана.
\textbf{Progress awareness} — ахиц, үлдсэн ажил тод харагдана.
\end{defbox}

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item \textbf{Task-first design:} хэрэглэгч нэг даалгаврыг хамгийн бага алхмаар гүйцэтгэх боломжтой байх;
    \item \textbf{Consistency:} веб ба мобайл дээр нэршил, үйлдлийн логик ижил байх;
    \item \textbf{Feedback visibility:} үйлдлийн үр дүнг (хадгалсан, баталгаажсан, оноо өссөн гэх мэт) шууд харуулах;
    \item \textbf{Progress awareness:} хэрэглэгч өдөр тутмын ахиц, үлдсэн даалгавраа шууд харах боломжтой байх.
\end{itemize}

Эдгээр зарчим нь суралцах орчинд хэрэглэгчийн когнитив ачааллыг бууруулж, тогтвортой ашиглалтыг бий болгох зорилготой.

\subsubsection{Дизайн системийн бүтэц}

Веб болон мобайл хоёулаа нийтлэг дизайн системийг Figma дээр боловсруулсан бөгөөд дизайн системд дараах гурван давхаргыг тусгасан:

\begin{enumerate}[leftmargin=2em, itemsep=0.25em]
    \item \textbf{Токен давхарга:} өнгөний палитр, хэмжээ, үсгийн стиль, зай (spacing) — веб болон мобайлд нийтлэг;
    \item \textbf{Компонентын давхарга:} товч, карт, хүснэгт, навигаци зэрэг дахин ашиглах боломжтой элементүүд;
    \item \textbf{Хуудасны загвар:} модуль бүрийн wireframe болон high-fidelity прототип.
\end{enumerate}

Figma-аас веб тал Next.js/Tailwind CSS руу, мобайл тал Flutter руу дизайн токеныг нийцүүлэн хэлбэрчилсэн нь платформ хоорондын харагдах байдлын тогтвортой байдлыг хангасан.

Файл хадгалалт & Supabase Storage & S3-нийцтэй; зураг, аудио, PDF \\ \hline
API холболт & REST (Supabase client) & Веб ба мобайлд нийтлэг, бичих хялбар \\ \hline
OCR & Tesseract.js / ML Kit & Тексттэй зурагнаас үг ялган авах \\ \hline
Дизайн хэрэгсэл & Figma & Wireframe, prototype, дизайн систем \\ \hline
Хувилбарын хяналт & Git / GitHub & Хамтран ажиллах, код хянах \\ \hline
\end{tabular}
\end{table}

Технологийн сонголтын үндэслэлийг илүү нарийвчлан авч үзвэл:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item \textbf{Next.js:} server-side rendering нь SEO болон анхны ачааллын хурдыг сайжруулдаг; React-ын экосистем нь хурдан хэрэгжүүлэх боломжийг олгодог;
    \item \textbf{Expo (React Native):} iOS болон Android-д нэг кодбейс ашиглах нь хөгжүүлэлтийн ачааллыг эрс бууруулсан; OTA шинэчлэлт нь дэлгүүрт дахин гаргахгүйгээр алдаа засах боломж олгодог;
    \item \textbf{Supabase/PostgreSQL:} сургалтын өгөгдөл, хэрэглэгчийн контент, ранкингийн тооцоололд реляц загвар тохиромжтой; нэгдсэн auth, storage нь гуравдагч талын сервисийн хэрэгцээг багасгадаг;
    \item \textbf{Cloud storage:} зураг, аудио, медиа контентыг өгөгдлийн сангаас тусгаарлан хадгалах боломжийг олгоно;
    \item \textbf{REST API:} веб ба мобайлд нийтлэг өгөгдлийн эх үүсвэрийг бий болгодог;
    \item \textbf{Модульчлагдсан frontend:} шинэ функц нэмэх үед тусгаар хөгжүүлэх боломжтой байдаг.
\end{itemize}

Хөгжүүлэлтийн явцад дараах орчин, хэрэгслүүдийг ашигласан:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item \textbf{Код засварлагч:} Visual Studio Code — TypeScript, ESLint, Prettier нэмэлтүүдтэй;
    \item \textbf{Мобайл туршилтын орчин:} Expo Go апп болон Android/iOS эмулятор;
    \item \textbf{API туршилт:} Supabase Studio, Postman;
    \item \textbf{Хувилбарын удирдлага:} Git feature branch стратеги — модуль бүрийг тусдаа салбарт хөгжүүлж нэгтгэх;
    \item \textbf{Дизайн синхрончлол:} Figma дизайн системийг веб болон мобайл компонентуудад нийцүүлэн хэрэглэх.
\end{itemize}

\subsection{Хэрэгцээт алгоритмууд}

\subsubsection{Spaced Repetition алгоритм}

FutureHub-ийн флашкарт давталтын хэсэгт \textbf{SM-2 (SuperMemo 2)} алгоритмд суурилсан зайтай давталтын (Spaced Repetition System, SRS) логикийг хэрэгжүүлсэн. SM-2 алгоритм нь карт бүрийн \textbf{давталтын интервал}, \textbf{хүндрэлийн коэффициент}, \textbf{зөв/буруу хариултын түүх}-ийг харгалзан дараагийн давталтын огноог тодорхойлдог.

Энэхүү логик нь дараах практик үр нөлөөг өгдөг:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item өдөр бүр ижил тооны карт механикаар давтах ачааллыг бууруулна;
    \item картын хэцүү түвшинд тохируулан суралцах үр ашгийг нэмэгдүүлнэ;
    \item хэрэглэгчийн цагийн нөөцөд нийцсэн ухаалаг давталт үүсгэнэ.
\end{itemize}

Backend-д карт бүрийн \texttt{ef}, \texttt{interval}, \texttt{repetitions}, \texttt{next\_review} талбаруудыг хадгалж, давталт хийх бүрт эдгээрийг шинэчилдэг. Хэрэглэгч тухайн өдрийн давталтаа нээх үед \texttt{next\_review <= today} нөхцлийг хангасан картуудыг API татаж ирдэг.

\begin{keybox}[SRS-ийн сонголтын гол шийдэл]
SM-2 логикийг \textbf{клиент түвшинд биш, backend түвшинд} бүрэн хэрэгжүүлсэн. Үүний үр дүнд веб болон мобайл клиент хоёулаа \textbf{нэг тогтвортой давталтын хуваарь} ашиглах бөгөөд хэрэглэгч нэг төхөөрөмж дээр хариулсан давталт нөгөө төхөөрөмж дээр шууд тусгагдана.
\end{keybox}

\subsubsection{OCR интеграцийн аргачлал}

OCR урсгалыг FutureHub дотор дараах \textbf{таван алхамт} аргачлалаар зохион байгуулсан:

\begin{keybox}[OCR $\rightarrow$ флашкарт pipeline]
\textbf{Зураг} $\rightarrow$ \textbf{Танилт \& засвар} $\rightarrow$ \textbf{Толь бичигтэй тулгах} $\rightarrow$ \textbf{Флашкарт руу хадгалах} $\rightarrow$ \textbf{Эхний интервал тохируулах}.
\end{keybox}

\begin{enumerate}[leftmargin=2em, itemsep=0.25em]
    \item хэрэглэгч зураг оруулах;
    \item танигдсан текстийг урьдчилан засварлах интерфейсээр баталгаажуулах;
    \item баталгаажсан үгийг толь бичгийн хайлттай холбох;
    \item шинэ эсвэл сайжруулсан утгыг флашкарт руу хадгалах;
    \item үүсгэсэн картын давталтын эхний интервалыг автоматаар тохируулах.
\end{enumerate}

Энэхүү урсгал нь зураг дээрх нэр томьёог шууд суралцах нэгж болгон хөрвүүлэх боломжийг олгож, ялангуяа гадаад хэл дээрх материалтай ажиллах үед хэрэглэгчийн ачааллыг бууруулна. OCR хөдөлгүүр болгон \textbf{мобайл талд ML Kit (Google)}, \textbf{веб талд Tesseract.js}-ийг тус тус ашиглаж, хэлний онцлогоос хамааран танилтын нарийвчлалыг хослуулсан.

\subsection{Модуль тус бүрийн хөгжүүлэлт}

Хөгжүүлсэн үндсэн модулиуд нь Flashcard, Dictionary, Blog/Article, Discussion, Project log, Contest, Profile \& Contribution ranking юм. Модуль тус бүрийн хөгжүүлэлтэд баримталсан гол зарчмуудыг дараах байдлаар тодорхойлов:

\begin{itemize}[leftmargin=2em, itemsep=0.25em]
    \item \textbf{Flashcard module:} картын lifecycle (үүсгэх, давтах, архивлах)-ийг төв болгож SM-2 алгоритмыг backend түвшинд хэрэгжүүлсэн;
    \item \textbf{Dictionary module:} нэр томьёоны утга, орчуулга, жишээ, эх сурвалжийн бүтэцтэй; флашкарт болон нийтлэлтэй хоёр талт холбоостой;
    \item \textbf{Blog/Article module:} Markdown дээр суурилсан хөнгөн агуулгын урсгал; draft/published төлвийн удирдлагатай;
    \item \textbf{Discussion module:} асуулт-хариулт ба санал үнэлгээ; хамгийн хэрэгтэй хариултыг accepted болгох механик;
    \item \textbf{Project log module:} хугацааны дарааллаар ажлын явц бичих боломж; milestone-тэй холбоотой;
    \item \textbf{Contest/Course module:} оролцоо, хугацаа, дүнгийн үндсэн логик; багшийн эрхээр удирддаг;
    \item \textbf{Ranking module:} олон эх сурвалжаас ирэх хувь нэмрийн оноог (нийтлэл, карт, хариулт, тэмцээн) нэгтгэн тооцох; хэрэглэгчийн contribution breakdown харагдах.
\end{itemize}

Хөгжүүлэлтийн явцад модуль бүрийг тусгаар туршиж, дараа нь API түвшинд нэгтгэх хэлбэрээр алдааны нөлөөллийг хамгийн бага түвшинд хязгаарласан.

\subsection{Git салбарын стратеги}

Хувилбарын удирдлагад feature branch стратеги ашигласан:

\begin{itemize}[leftmargin=2em, itemsep=0.2em]
    \item \texttt{main} салбар — тогтвортой, туршигдсан хувилбар;
    \item \texttt{feature/<module-name>} — модуль бүрийн хөгжүүлэлт тусдаа салбарт;
    \item pull request болон code review-ийн дараа \texttt{main}-д нэгтгэх.
\end{itemize}

Ийм аргачлал нь модуль нэгтгэх үеийн мөргөлдөөнийг (merge conflict) бууруулж, кодын чанарыг хянах боломж олгосон.

Системийн туршилтыг unit test (тус бүрийн функц шалгах), integration test (модуль хоорондын уялдаа шалгах) болон user acceptance test (хэрэглэгчийн урсгалын туршилт) гэсэн гурван түвшинд хийсэн. Туршилтын үр дүнд илэрсэн алдаа, гүйцэтгэлийн асуудлуудыг засварлаж, UI болон алгоритмын сайжруулалтыг нэгдсэн SDLC-ийн сайжруулах үе шатад буцаан оруулсан.

\subsection{Туршилтын сценарийн бүтэц}

Туршилтын сценари тус бүрийг дараах \textbf{таван хэсэгт} задалсан бүтэцтэй боловсруулсан:

\begin{defbox}[Туршилтын сценарийн 5 хэсэгт бүтэц]
\textbf{1. Урьдчилсан нөхцөл} — эрх, өгөгдлийн төлөв. \textbf{2. Алхам} — хэрэглэгчийн үйлдэл. \textbf{3. Хүлээгдэж буй үр дүн} — зөв гүйцэтгэлийн тайлбар. \textbf{4. Бодит үр дүн} — ажиглагдсан гаралт. \textbf{5. Зөрүү ба арга хэмжээ} — алдааны шалтгаан, засварын төлөвлөгөө.
\end{defbox}

\begin{enumerate}[leftmargin=2em, itemsep=0.25em]
    \item урьдчилсан нөхцөл (хэрэглэгчийн эрх, өгөгдлийн төлөв);
    \item туршилтын алхам;
