\section{Судалгааны төрөл}

Энэхүү дипломын ажил нь хэрэглээний судалгаа (applied research) төрөлд хамаарна. Онолын үр дүнг шууд практик бүтээгдэхүүн болгон хэрэгжүүлэх зорилготой бөгөөд КУТ-ийн оюутнуудын суралцах орчинд тулгамдаж буй бодит асуудлыг шийдвэрлэхэд чиглэсэн. Судалгааны гаралт нь ажиллагаатай веб болон мобайл апп бүхий туршилтын систем юм.

\subsection{Хөгжүүлэлтийн загвар}

Энэхүү системийг хөгжүүлэлтийн шугаман (Waterfall) болон спираль (Spiral) загваруудын давуу талыг нэгтгэсэн Hybrid (Iterative) загвараар боловсруулсан. Уг загвар нь төслийн эрсдэлийг бууруулах, модулиудыг тасралтгүй сайжруулах боломжийг олгодог.

\subsubsection{Hybrid(Iterative) загварыг сонгосон үндэслэл}

\begin{itemize}[leftmargin=2em]
	\item Уян хатан байдал: Шаардлага бүрэн тодорхой болоогүй үед эхний итерацаар суурь функцийг хөгжүүлж, дараагийн шатанд нэмэлт өөрчлөлтийг тусгах боломжтой.
	\item Эрсдэлийн удирдлага: Модуль тус бүрийг тусгаарлаж хөгжүүлснээр гарч болох алдаа, техникийн хүндрэлийг эрт шатанд илрүүлж засах нөхцөл бүрдсэн.
	\item Чанарын хяналт: Шат бүрийн төгсгөлд туршилт хийгдэх тул эцсийн бүтээгдэхүүний чанар сайжирна.
\end{itemize}

\subsubsection{Хөгжүүлэлтийн үе шатууд (Iterative Cycles)}

Модуль бүр дээр дараах итерацийн дарааллыг баримталсан:

\begin{itemize}[leftmargin=2em]
	\item Шаардлага тодорхойлох (Analysis): Тухайн модулийн гүйцэтгэх үүрэг, хэрэглэгчийн хэрэгцээг нарийвчлан тогтоох.
	\item Загварчлал (Design): Өгөгдлийн сангийн бүтэц, хэрэглэгчийн интерфейс (UI/UX) болон логик архитектурыг төлөвлөх.
	\item Хөгжүүлэлт (Implementation): Сонгосон технологийн дагуу кодын бичиглэл хийх.
	\item Туршилт (Testing): Модулийн үйл ажиллагааг шалгаж, алдааг засварлах (Debugging).
	\item Сайжруулалт \& Үнэлгээ (Review): Туршилтын үр дүнд тулгуурлан дараагийн итерацид орох нэмэлт өөрчлөлтүүдийг төлөвлөх.
\end{itemize}

\subsection{Судалгааны объект, субъект, орчин}

\begin{itemize}
	\item Судалгааны объект: КУТ-ийн оюутнуудад зориулсан дижитал орчны загвар
	\item Судалгааны субъект: оюутан, багш, админ гэсэн хэрэглэгчийн гурван үндсэн бүлэг
	\item Судалгааны орчин: веб болон мобайл клиент, REST API, Supabase/PostgreSQL өгөгдлийн сан
\end{itemize}

\subsection{Ашигласан аргуудын нэгтгэл}

Системийн шийдлийг тодорхойлоход дараах аргуудыг хослуулан ашигласан.

\begin{enumerate}[leftmargin=2em]
	\item Баримт бичгийн шинжилгээ: ижил төрлийн платформуудын функц, архитектур, хэрэглэгчийн урсгалыг судлах
	\item Харьцуулсан шинжилгээ: FutureHub-ийн модуль бүрийг төстэй системтэй харьцуулж шаардлагын түвшинг тогтоох
	\item Загварчлалын арга: UML (use case, activity, sequence, class) болон ER диаграмаар системийн бүтэц, урсгалыг загварчлах
	\item Прототип хөгжүүлэлт: суурь функцуудыг богино мөчлөгөөр хэрэгжүүлж баталгаажуулах
	\item Туршилт-үнэлгээ: модуль, интеграц, хэрэглэгчид суурилсан чанарын шалгалт
\end{enumerate}

\subsection{Функциональ шаардлага}

Функциональ шаардлагыг \textit{core} болон \textit{extended} гэсэн хоёр ангиллаар авч үзсэн.

\subsubsection{Core шаардлага}

\begin{itemize}
	\item SRS давталт: флашкарт үүсгэх, засах, хуваалцах, SM-2 алгоритмаар давталтын хуваарь удирдах;
	\item Толь бичиг: нэр томьёо хайх, шинэ үг нэмэх, орчуулга ба жишээтэй бүртгэх;
	\item Нийтлэл: блог, нийтлэл, төслийн тэмдэглэл нийтлэх, markdown дэмжлэг;
	\item Асуулт-хариулт (Q\&A): хэлэлцүүлэг өрнүүлэх, санал өгөх, хариулт сонгох.
\end{itemize}

\subsubsection{Extended шаардлага}

\begin{itemize}
	\item Тэмцээн: хугацаатай тэмцээн зохион байгуулах, дүн гаргах;
	\item Сургалт: багш сургалт үүсгэх, оюутан хичээл дагах;
	\item Аналитик: хэрэглэгчийн ахиц, contribution-ий нэгтгэсэн тайлан.
\end{itemize}

\subsection{Функциональ бус шаардлага}

\begin{itemize}
	\item Гүйцэтгэл (Performance): нэг хэрэглэгчийн энгийн асуулгын хариу өгөх хугацааг мэдрэгдэхүйц сааталгүй байлгах; веб ба мобайл дээр өгөгдлийн тасралтгүй байдлыг API-ийн нэг эх сурвалжаар хангах;
	\item Аюулгүй байдал (Security): JWT-д суурилсан authentication, Row Level Security (RLS) бодлого, role-based access control;
	\item Өргөтгөх боломж (Scalability): контентын модуль нэмэгдэхэд өгөгдлийн загварыг дахин үндсээр нь эвдэхгүй өргөтгөх боломжтой байх;
	\item Хэрэглэхэд ээлтэй байдал (Usability): хэрэглэгч нэг даалгаврыг хамгийн бага алхмаар гүйцэтгэх, веб ба мобайл дээр нэршил, үйлдлийн логик нийцтэй байх.
\end{itemize}

\subsection{Хязгаарлалт (Constraints)}

\begin{itemize}
	\item Зөвхөн сургуулийн email хаягаар бүртгэл үүсгэх;
	\item Гадны хэрэглэгч бүртгүүлэхгүй, контентыг зөвхөн харах эрхтэй;
	\item Зарим модуль (жишээ нь тэмцээн, сургалт) хязгаарлагдмал байдлаар ажиллах.
\end{itemize}

\subsection{UML диаграммууд}

Системийн загварчлалд дараах UML диаграммуудыг боловсруулсан.

\subsubsection{Use Case диаграм}

Use case загварчлалын хүрээнд хэрэглэгчийн гол үйлдлүүдийг үүргээр бүлэглэн тодорхойлов.

\begin{itemize}
	\item Оюутан: бүртгүүлэх, нэвтрэх, карт үүсгэх, давтах, нийтлэл/асуулт нийтлэх, төслийн тэмдэглэл хөтлөх, сургалт/тэмцээнд оролцох;
	\item Багш: сургалт үүсгэх, агуулга бэлтгэх, чанарын хяналт хийх, зөвлөмж өгөх;
	\item Админ: хэрэглэгчийн эрх удирдах, агуулгын бодлого хэрэгжүүлэх, тайлан хянах.
\end{itemize}

\subsubsection{Activity диаграм}

Гол урсгалуудын дарааллыг activity диаграмаар загварчилсан. Үүнд: хэрэглэгч нэвтрэх, флашкарт давтах, нийтлэл нийтлэх, тэмцээнд оролцох зэрэг урсгалууд багтана. Урсгал бүр нь эхлэл, шийдвэр, үйлдэл, төгсгөлийн цэгүүдтэй бөгөөд хэрэглэгчийн үүргээс хамааран салбарлалт үүсдэг.

\subsubsection{Sequence диаграм}

Системийн гол харилцан үйлчлэлүүдийг sequence диаграмаар дэлгэрүүлсэн. Ялангуяа:

\begin{itemize}
	\item Флашкарт давтах урсгал: хэрэглэгч → клиент → API → SRS логик → өгөгдлийн сан → хариу буцаах;
	\item OCR урсгал: хэрэглэгч зураг оруулах → OCR engine → текст таних → урьдчилан засах → толь бичиг/флашкарт руу хадгалах.
\end{itemize}

\subsubsection{Class диаграм}

Системийн үндсэн объектуудын хамаарлыг class диаграмаар тодорхойлсон. Гол entity-үүд нь: User, Flashcard, DictionaryEntry, Article, Discussion, ProjectLog, Contest, Ranking бөгөөд тэдгээрийн хоорондын холбоос (нэг-олон, олон-олон)-ыг тусгасан.

\subsection{Архитектурын шийдэл}

Системийг клиент–сервер архитектур дээр суурилан боловсруулсан. Веб болон мобайл аппликейшн нь RESTful API-гаар дамжин Supabase backend сервертэй холбогдож, өгөгдлийг PostgreSQL өгөгдлийн санд хадгална.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.98\textwidth]{pictures/Системийн архитектур.png}
\caption{FutureHub системийн клиент-сервер архитектур}
\label{fig:system-architecture}
\end{figure}

Зураг~\ref{fig:system-architecture}-т архитектурын мэдээллийн урсгалыг харуулсан. Клиентээс API хүсэлт ирж, backend нь өгөгдлийн (metadata) асуулгыг PostgreSQL-с, файл төрлийн агуулгыг cloud storage-оос тус тус шийдэн хэрэглэгчид буцаадаг. Мультимедиа контент ихсэх үед өгөгдлийн сангийн ачааллыг тусгаарлах давуу талтай.

\subsubsection{Deployment бүтэц}

\begin{itemize}
	\item Web: Next.js аппликейшныг Vercel дээр deploy хийсэн;
	\item Mobile: Flutter аппликейшныг Expo-оор sideload болон store-д зориулан бэлтгэсэн;
	\item Backend: Supabase BaaS (Backend as a Service) — PostgreSQL, Auth, Storage, Edge Functions нэгдсэн.
\end{itemize}

\subsubsection{Authentication урсгал}

Хэрэглэгчийн нэвтрэлтийг дараах бүтцээр хэрэгжүүлсэн:

\begin{itemize}
	\item JWT (JSON Web Token): Supabase Auth-оор token үүсгэж, клиент талд хадгалах;
	\item RLS (Row Level Security): өгөгдлийн сангийн түвшинд хэрэглэгч зөвхөн өөрийн эрхтэй мөрүүдэд хандах;
	\item RBAC (Role-Based Access Control): оюутан, багш, админ гэсэн үүргээр хандалтыг ялгах.
\end{itemize}

\subsubsection{Алдааны удирдлагын стратеги}

API түвшинд алдааг стандарт HTTP status code (400, 401, 403, 404, 500)-оор ангилж, клиент талд хэрэглэгчид ойлгомжтой мэдэгдэл харуулах зарчмыг баримталсан. Мөн алдааны лог Supabase dashboard-аар хянагдана.

\subsubsection{API дизайн}

API-г resource-oriented REST зарчмаар дизайлсан. Үндсэн endpoint-ууд:

\begin{itemize}
	\item \texttt{/auth/*} — бүртгэл, нэвтрэлт, token шинэчлэл;
	\item \texttt{/cards/*} — флашкарт CRUD, давталтын төлөв;
	\item \texttt{/dictionary/*} — толь бичгийн хайлт, нэмэлт;
	\item \texttt{/articles/*} — нийтлэл CRUD;
	\item \texttt{/discussions/*} — асуулт-хариулт, санал;
	\item \texttt{/projects/*} — төслийн тэмдэглэл;
	\item \texttt{/contests/*} — тэмцээний удирдлага;
	\item \texttt{/rankings/*} — ранкингийн тооцоолол, жагсаалт.
\end{itemize}

\subsection{Алгоритмын шийдлүүд}

\subsubsection{Flashcard / SRS систем}

FutureHub-ийн флашкарт давталтын хэсэгт SM-2 (SuperMemo 2) алгоритмыг backend түвшинд хэрэгжүүлсэн. Карт бүр дараах параметрүүдтэй:

\begin{itemize}
	\item \texttt{ef} — easiness factor (хялбаршлын коэффициент, анхны утга 2.5);
	\item \texttt{interval} — дараагийн давталт хүртэлх хоног;
	\item \texttt{repetitions} — амжилттай давтсан тоо;
	\item \texttt{next\_review} — дараагийн давталтын огноо.
\end{itemize}

Давталтын интервалыг дараах томьёогоор тооцоолно:

\[
I_1 = 1, \quad I_2 = 6, \quad I_n = I_{n-1} \times EF \quad (n \ge 3)
\]

Хялбаршлын коэффициентийг хэрэглэгчийн үнэлгээ $q \in [0,5]$ үед шинэчилнэ:

\[
EF' = EF + \left(0.1 - (5 - q)\left(0.08 + (5 - q) \cdot 0.02\right)\right), \qquad EF' \ge 1.3
\]

Хэрэв $q < 3$ бол давталтын тоог дахин эхнээс эхлүүлж, карт богино хугацаанд дахин давтагдана.

\paragraph{OCR → карт үүсгэх pipeline.}

OCR урсгалыг дараах алхмуудаар зохион байгуулсан:

\begin{enumerate}[leftmargin=2em]
	\item хэрэглэгч зураг оруулах (камер эсвэл галерей);
	\item OCR engine (ML Kit / Tesseract.js) текст таних;
	\item танигдсан текстийг урьдчилан засварлах интерфейсээр баталгаажуулах;
	\item баталгаажсан үгийг толь бичгийн хайлттай холбох;
	\item шинэ эсвэл сайжруулсан утгыг флашкарт руу хадгалах;
	\item үүсгэсэн картын давталтын эхний интервал автоматаар тохируулах.
\end{enumerate}

\subsubsection{Contribution Ranking систем}

Хэрэглэгчийн хувь нэмрийн нэгтгэсэн оноог дараах томьёогоор тооцоолно:

\[
\text{Score} = w_f \cdot F + w_d \cdot D + w_a \cdot A + w_q \cdot Q + w_p \cdot P
\]

энд:
\begin{itemize}
	\item $F$ — флашкартын идэвх (үүсгэсэн, давтсан тоо);
	\item $D$ — толь бичигт оруулсан хувь нэмэр;
	\item $A$ — нийтэлсэн нийтлэлийн тоо, чанар;
	\item $Q$ — Q\&A хэсэгт асуусан/хариулсан тоо;
	\item $P$ — төслийн тэмдэглэлийн идэвх;
	\item $w_f, w_d, w_a, w_q, w_p$ — модуль тус бүрийн жин.
\end{itemize}

Жингийн тэнцвэрийн зарчим: нэг модульд хэт их ачаалал өгөхгүй байхын тулд жингүүдийн нийлбэрийг нормчилж, модуль бүрийн хувь нэмрийг тэнцвэртэй тусгана. Хэрэглэгч оноо яаж өссөн шалтгааныг модуль тус бүрээр задлан харах боломжтой.

\subsubsection{Хайлтын алгоритм}

\begin{itemize}
	\item Tag-based search: контент бүрт tag холбож, tag-аар шүүх;
	\item Full-text search: Supabase-ийн PostgreSQL дээрх \texttt{tsvector}/\texttt{tsquery}-г ашиглан толь бичиг, нийтлэлийн бүтэн текст хайлт хийх.
\end{itemize}
